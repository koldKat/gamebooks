CSS file split (2026-07-18)

style.css had grown to 9,238 lines - one file for the whole app. Split into 15 per-module files (one per like-named JS module) plus style.css itself, now 549 lines of shared/base rules only. public-profile.css is shared by both public-profile.js and covers.js (cover activity view lives in the same #public-modal markup both use).

Unlike JS, there's no import-cascade to maintain between stylesheets - each is an independent <link>, so a changed CSS file only needs its own ?v=N bumped. reduce-motion.css and mobile.css are cross-cutting overrides rather than one module's styling, so they're deliberately the last two <link> tags in index.html - an improvement over the original file, where those two sections sat at arbitrary mid-file positions.

Verified via exact line-range extraction plus a line-count reconciliation (sum of all new files + planned remainder must equal the original total) before every trim of the source file - this caught two real extraction mistakes before they reached the live file. See project_refactor_main.md memory for the full account.

Follow-up bug, fixed 2026-07-19: server.js's computeCodeStats() (feeds "Lines of code"/"Code size" in Stats for Nerds) hardcoded a single filename, 'public/css/style.css', instead of scanning the public/css/ directory - missed when the split shipped. Silently dropped ~8,700 CSS lines from both stats. Fixed to fs.readdirSync('public/css'), matching the pattern already used for public/js/admin. Needs a server restart (one-time IIFE at module load, not per-request).

Server file split (2026-07-26)

server.js (3,743 lines) and server/db.js (6,373 lines) were the last two monolithic files in the codebase. Same process as the CSS split above: build each new module fully, verify it, wire it in, delete the old code from the monolith last - never a bulk line-range removal.

server/db.js is now a thin barrel (713 lines): every raw CREATE TABLE/ALTER TABLE/one-time-migration block stays physically in db.js, in its original relative order - some migrations reference tables/functions defined much later in the original file purely because production's live database already has those tables from earlier deployments, so reordering the DDL was judged unsafe. Only the function definitions moved out, into server/db/*.js domain modules (see project structure above). db.js's final module.exports re-exports the exact same 233 named functions it did before the split.

server.js is now 597 lines: requires, one-time bootstrap, the Router (regex route-pattern constants + one large dispatch function), and the final httpServer.listen(...). Everything else moved into server/*.js (cross-cutting: SSE, email, request helpers, runtime/process state, static file serving) and server/routes/*.js (per-domain HTTP handlers). Mutable process state that used to be bare module-level let bindings (maintenance-mode flag, traffic counters, CPU/memory averages, uptime timestamps) was extracted into server/runtime-state.js behind getter/setter accessors, since raw let variables can't be shared by reference across CommonJS modules.

Verification: server.js can never actually be run to test (it ends in a live httpServer.listen(...), and the "never restart the server" rule forbids running it), so every new/rewritten file passed node --check, then was actually require()-d in isolation to catch load-time errors --check misses. A third pass - a script cross-referencing every bare identifier( call in a file against its locally-defined/required names - caught the class of bug the first two miss entirely: a name that's fine at module-load time but undefined the moment a handler actually runs. This caught several real missing-import bugs (authenticate/addSecurityHeaders in routes/admin.js, tokenFromReq/isLocalhost in routes/books.js, sendAdminEmail/escapeHtml in routes/forum.js, and fs/path/ATTACHMENTS_DIR in routes/forum.js's handleForumDeleteThread). The server/db.js barrel's export count was diffed before and after every step and stayed at exactly 233 throughout.

Server

server.js is a plain Node.js HTTP server. It serves static files from public/ and exposes a JSON REST API. Routes are matched manually with regex - no express or other framework.

Listens on port 443 (HTTPS) when a Let's Encrypt certificate exists at /etc/letsencrypt/live/koldkat.net/, otherwise falls back to port 3000 (HTTP). Port overridable via PORT env var. HTTP port (redirect) defaults to 80, overridable via HTTP_PORT.

Book PDFs

PDF files are stored in public/books/<bookId>_<timestamp>.pdf and served via GET /books/<filename>.

  • POST /api/books/:id/pdf - raw PDF body, max 128 MB. Magic bytes %PDF validated. Old file deleted on replacement. Awards 200 XP (pdf_available) to every user who has the book in their library (once per user per book).
  • DELETE /api/books/:id/pdf - removes the file and clears pdf_path. Does not revoke previously awarded XP.

The pdf_path column on books stores the filename only.

The static file gate (GET /books/:path) requires the request to be authenticated with a user who has is_admin = 1 or pdf_access = 1. Unauthenticated requests and users without either flag receive 403. pdf_access is toggled by the admin via POST /api/admin/users/:id/pdf-access with body { pdfAccess: bool }.

Gold Coins: base GC is still derived from XP, but extra one-time milestone GC rewards are stored separately in users.bonus_coins and deduped in coin_events.

  • playtime_24h - 1 GC each time a user crosses another 1,440 idle_heartbeat events (24 tracked hours)
  • book_completed - 1 GC the first time a user earns visit_all for a book
  • runs_milestone - 1 GC per 100 completed runs (win_run + death_run + battle_run events total); ref is the milestone as a string ("100", "200", …). Checked at runtime after every run-completing state save and backfilled once at startup.
  • visit_all_series - N GC (N = child book count) the first time a user earns visit_all for every non-container book in a series
  • visit_all_anthology - N GC (N = child book count) the first time a user earns visit_all for every child book of an anthology

Startup backfills for book_completed, runs_milestone, visit_all_series, and visit_all_anthology run once, guarded by book_complete_coin_backfilled, runs_milestone_coin_backfilled, and group_complete_coin_backfilled keys in admin_settings.

Admin panel UI

All admin UI documentation (stat cards, tabs, user actions, book actions, feedback, announcements, SMTP config, and admin settings keys) is in admin/admin-guide.html, served at /admin/guide.

Stats polling

GET /api/admin/stats - full stats payload: users, books (non-demo non-container top-level), anthologies (is_container = 1 top-level non-demo), series (all rows in series table), sessions, sections, playthroughs, wins, deaths, DB size, coins totals (earned / available / spent), uptime fields, traffic counters. Polled every 60 s by the admin panel (loadStats).

GET /api/admin/live - cheap subset for high-frequency polling: { heapUsed, heapTotal, rss, cpuPct, sessionUptime, appAge, trafficIn, trafficOut }. CPU% is a one-decimal float derived from process.cpuUsage() delta between calls. sessionUptime and appAge are seconds since the current session start and since first-ever tracking, respectively. Polled every 1 s by loadLive(). Drives the Heap, RSS/CPU, Session Uptime, App Age, and Traffic cards.

Traffic counters

_trafficIn / _trafficOut accumulate raw bytes across all HTTP requests and response bodies. Flushed to admin_settings keys traffic_in / traffic_out every 50 requests and on SIGINT/SIGTERM. Returned by both /api/admin/stats and /api/admin/live.

Uptime tracking

Five keys in admin_settings drive uptime metrics: server_first_tracked_at (set once, never overwritten), server_session_start_at (reset when restart gap > 5 s), server_total_downtime_s (accumulated downtime), server_last_heartbeat (written every 30 s), server_stopped_at (written on clean shutdown, cleared to 0 on next start). _sessionStartAt is cached in memory at startup for zero-DB-read serving on every live poll. "App Age" is now − getAppBirthTimestamp(), where getAppBirthTimestamp() returns MIN(created_at) across the users and books tables - the date the first user ever registered. "Session Uptime" is now − _sessionStartAt. Both update every second via the live endpoint.

Membership is explicit via user_series - a series only appears in a user's list if they have a row there:

XP & levelling

XP is stored in users.xp. Every awarded event is recorded in xp_events with a UNIQUE constraint on (user_id, event, ref) - XP can never be double-awarded.

Level formula

xpForLevel(n)    = 1000 × n × (n+1) / 2
computeLevel(xp) = min(floor((-1 + sqrt(1 + 8·xp/1000)) / 2), 100)

Level 1 = 1,000 XP · Level 10 = 55,000 · Level 100 = 5,050,000 (cap)

Undo & fast travel limits

Both maxUndos() and maxFastTravels() follow the same formula: 3 at levels 0–30, then +1 per 10 levels from level 31 (thresholds: 31, 41, 51, 61, 71, 81, 91), capped at 10. When a level-up crosses a threshold, the feed announces it as a · +1 undo & fast travel unlocked (N per run) suffix on the level-up entry.

Per-run reward ref bug, fixed 2026-07-19 (real XP loss, not cosmetic): death_run/battle_run/win_run/share_run/charsheet_run/charsheet_saved/run_depth used to key their dedup ref off the run's array index in playthroughs (${bookId}:${i}). Array slots aren't stable - deleting a run and having a later, unrelated run land on the same index makes the new run's reward collide with the deleted run's leftover xp_events row and get silently swallowed by INSERT OR IGNORE, with no error or log. run_depth (fires on nearly every run) was the most common victim purely because it's the most frequent of the group. Fixed by keying the ref off the run's own startedAt timestamp instead - assigned once at creation, never reused, so two runs can never collide again.

Backfill (scripts/backfill_run_reward_refs.js, one-time, run 2026-07-19): scanned every user_books row; for each playthrough, checked whether its current state satisfies each of the 7 affected event types, and whether the old (index-based) ref has a stale row predating that run's own startedAt (proof it belongs to a deleted predecessor) or no row at all - awarding fresh via the real awardXp (correct boost/carry/level-up/coin handling, not a reimplementation) when so. Idempotent, safe to re-run. Result: 216 awards, 5,206 total XP, across 14 users. add_charsheet_field (also index-ref-scoped) was not included - a known small remaining gap.

run_depth stays index-based on purpose - a farming loop found and corrected the same day. The startedAt fix is right for the other 6 events (each represents real, distinct effort, deserving credit even at a reused slot). run_depth is different - starting a run costs nothing, so a guaranteed-unique ref made it directly farmable via create-run/delete-run/repeat.

A first attempt over-corrected this to a one-time-per-book bonus (like first_win/first_loss) - this was wrong and reverted the same day. Animated XP gain (client, profile.js)

The books-screen and play-area XP bars/counters (not the profile modal, which always snaps instantly) tween whenever renderBooksXpSummary(data, { fromXp }) is called with a known previous XP value. Duration scales with the user's level: level * XP_ANIM_MS_PER_LEVEL (100ms/level, so lvl 37 = 3.7s, lvl 100 = 10s); level 0 renders instantly. _animateXpTo interpolates linearly (not eased) from the last value actually painted to the target, recomputing the level bounds every frame from the interpolated value - so a level-up crossed mid-animation naturally shows the bar filling to 100%, resetting, and continuing in the new level with no special-casing. A generation counter invalidates any in-flight animation frame loop when a newer update arrives (rather than queuing), so a new tween always starts from wherever the bar currently sits. Linear interpolation was chosen specifically so a restart never reintroduces a fast-start burst partway through an in-progress deceleration. rewards.js › _processRewardSnapshot supplies fromXp by tracking the last known XP across snapshot pushes; direct instant calls with no fromXp are used only for session-initial loads. The "(Y XP)" figure in the boost line tweens in lockstep with the main counter (same t, same frame, tracked via a parallel _displayedBoostXp) - _renderXpSummary no longer renders that line itself, only _xpApply/_animateXpTo do, so it can't fall out of sync or snap ahead of the main counter. This used to read "(Y XP earned)"; the word "earned" was dropped as useless filler, not the figure itself. The profile modal's own boost line (renderXpBlock) is untouched and always instant.

Backed by GET /api/app-xp → db.getAppXpSummary(): level/title/levelXp/nextLevelXp use the same quadratic formula as a per-user bar but scaled by Math.max(1, users * 1000) - identical to appLevelScale in getSiteStats() (Stats for Nerds' "App level"). xp is SUM(users.xp), the same number getSiteStats() reports as "Total XP earned" - that panel renders it through fmt() which compacts to K/M/B above 10,000, so the two figures agree even though they look different at a glance. xpBoostPct is SUM(users.xp_boost_pct) / 10 - every user's currently-active boost rate added together (same "sum everyone's rate" shape as heartbeatRatePerMin), not a retrospective "% of XP earned via boost" ratio, since that answers a different question from "how much boost is running right now app-wide". heartbeatRatePerMin sums every user's passive rate as if everyone were online at once: users + (SUM(bonus_heartbeat_xp) + SUM(max(0, level-10))) * 0.1, computed in raw SQL (mirroring the existing avgLevelRow quadratic-in-SQL pattern) to avoid a second full-table round trip. Deliberately staggered, not fired in the same tick as loadFeed(): a plain state save carries no reward data in its response, so a viewer's own personal XP bar only actually updates via loadFeed()'s own scheduleRewardProfileRefresh(150) call. Both the 60s poll and the SSE debounce call loadFeed() and refresh the App/Avg-Level bars off the same trigger - if refreshAppXp() ran directly alongside loadFeed(), every site-wide activity trigger would fire the viewer's own 150ms-delayed personal-bar tween and the App/Avg-Level bars' tween from the exact same instant, every time. The app-xp stream's own trigger was added later, after the floaters were found to fire live while the bar's numbers sat stale until the next poll - _refreshAppXpStaggered() now debounces internally (a single tracked timer, cleared and rescheduled on each call) since that stream, unlike the other two triggers, can fire several times in quick succession and would otherwise queue one refetch per award instead of settling on one.

Completion percentage floor rule

Every "N out of total (X%)" display in the app (books-list progress bars, the play-area mapped/discovered counter, and every ratio in the Stats for Nerds modal) shows 100% only when n >= total exactly; otherwise the percentage is floored and capped at 99% (Math.min(99, Math.floor(n / total * 100))), never rounded up. This prevents e.g. 318/319 sections from displaying as a misleading "100%". Compact number formatting (Stats for Nerds)

stats.js's fmt - the shared formatter used for essentially every plain count in the modal - switches to the compact fmtCompact form (K/M/B/T/Qa/Qi suffixes) once the absolute value reaches 10,000; below that it's the plain comma-separated form. Decimal precision increases one place per tier (K = 1 decimal, M = 2, B = 3, T = 4, …). This is universal rather than an allowlisted set of fields - any stat that grows past 10,000 picks up the compact form automatically, not just the ones that already run high today (Total XP earned, XP events, Total pages/sections, Mapped/Discovered sections). Percentage suffixes from pct() are computed from the raw underlying values and unaffected. Guards a rounding-boundary edge case where e.g. 999999 would naively format to "1000.0K" at the K tier - if .toFixed(tier) rounds up to 1000 or more, the tier bumps up one level and redivides, correctly showing "1.00M" instead. Lines of code used to have its own hand-rolled (n/1000).toFixed(1)+'K' formatting that bypassed fmt entirely - always dividing by 1000 and always showing "K" regardless of scale, ignoring the 10,000 floor and never rolling over to "M". Switched to plain fmt(s.linesOfCode) for consistency.

Password hashing & sessions

Password hashing

crypto.scrypt (Node built-in, promisified) with a random 16-byte hex salt. Stored as { password_hash, salt }. Verification uses crypto.timingSafeEqual.

Sessions

Random 32-byte hex token stored in sessions table. Sent to client on login/register; stored in localStorage under gamebook_auth_token.

Sessions expire 7 days after creation (expires_at = created_at + 604800). getSession rejects expired tokens → client receives 401 and is redirected to login. Expired rows are deleted on server startup and on Vacuum.

Rate limiting

IP-level: Max 10 failed auth attempts per IP per 15 minutes. Tracked in memory (_authFailures Map); stale entries evicted on a 15-minute interval. Returns 429.

Account-level: After 5 consecutive failed login attempts, the account is temporarily locked for 15 minutes (locked_until = now + 900). Returns 403 with a descriptive message. failed_login_attempts resets to 0 on successful login or when the temp lock expires. Admin can hard-lock any non-protected account (locked_until = -1); hard locks never auto-clear. Protected accounts skip all lock logic.

Image upload security

Avatars and book covers are validated for magic bytes (JPEG, PNG, GIF, WebP) and compressed client-side to ≤256 KB before upload. Server enforces a 300 KB raw body limit.

Day-card cover backgrounds: each .feed-day-card gets a stack of tiles cycling through every distinct public book played that day, purely client-side in feed.js - no server changes needed. _dayCovers(items) (previously _prominentCoverForDay, which only returned a single "winner") tallies entries with bookId && bookIsPublic and a resolvable cover per book, then returns all distinct qualifying covers sorted by entry count descending - a day with several different books played shows more than just one of them, cycling through the list rather than repeating a single book. Each qualifying day's cover list is pushed onto _lastDayCoverLists (reset every loadFeed() call); the card gets data-day-index plus an empty .feed-day-cover-stack child, with the header/entries wrapped in a sibling .feed-day-content.

This is not a repeating CSS background - background-repeat can only tile one image, and cycling through different covers needs each tile to have its own image, so _applyDayCoverFlows(root) builds real DOM elements, placed outward from the vertical center, not from the top:

  • The most-prominent book (covers[0], or centerIdx - see below) is placed whole, at full card width and its own true aspect-ratio height (no stretch, no crop), centered so its own vertical middle lands on the card's vertical middle.
  • A pool of the day's other books (every index except the center one; a day with only one book falls back to that same book so it can repeat outward too) is drawn from independently by each side - downPtr/upPtr are separate counters into the pool, started half a pool-length apart. With exactly one other book the pool has one entry, so both sides land on it every time (a two-book day shows the same "other" book above and below); with two or more other books, the offset counters mean the two sides draw different books at any given ring, only converging once every other book has cycled through at least once.
  • Each side keeps extending its own edge and placing the next pool tile flush against the previous one (no gaps, no overlaps) until that edge passes the card's boundary, with a guard < 400 iteration cap as a hard safety net (a tile whose image fails to load nudges its edge by 1px instead of stalling).
  • centerIdx is normally 0 but falls back to whichever book's cover actually loaded if that specific one failed - otherwise a broken image for just the center book would still reserve its full-height band and start the outward tiling from its edges, while never placing anything to fill that band, leaving a blank gap in the middle.

A flat, constant-opacity overlay (.feed-day-cover-stack::after, rgba(31,41,55,0.9)) sits on top of the tiles - a top-to-bottom gradient was tried first and reverted, since past its final stop the color holds flat, so on a tall stack everything below the ramp sat at its darkest stop uniformly. .feed-day-content carries position: relative; z-index: 1 so the header/entries paint above the stack despite coming after it in paint order otherwise. This deliberately does not reuse books.js's anthology-stack flow technique verbatim - that one spans one image across several separately-positioned sibling cards via a cross-card offset; a day-card is a single box filled from within, so no offset math applies either way. Re-applied on every feed render, and skipped entirely (no image loads at all) when body.no-feed-day-covers is set. Days with no qualifying book get a feed-day-card--glass class instead of a cover-stack - rather than drawing a copy of anything, it lets the real rotating landing background (#landing-bg-a/#landing-bg-b, position:fixed; z-index:-1) show through directly, like glass, always in sync since it's the same live element rather than a snapshot. Since that background is fixed (not scrolling with the feed), a glass card is a window onto whatever part of the image sits at its current on-screen position - varies by scroll position, like any photo has brighter/darker patches - so a light tint (rgba(31,41,55,0.25)) keeps every glass card reading as "a card" regardless of what's behind it at that moment, rather than being fully see-through.

Getting to that number took three tries: first shipped at rgba(31,41,55,0.45) (read as flat black against a real background - the ambient image already carries its own ~92%-dark gradient baked in for page-wide legibility, so stacking more darkening on top compounds fast); "fixed" by reusing the exact same rgba(31,41,55,0.9) value as .feed-day-cover-stack::after for what sounded like a principled byte-identical tint, but a cover-tile is the raw, undimmed image before that 0.9 overlay applies, while the ambient background is already dimmed before any card-level tint - stacking 0.9 on an already-0.92-dimmed image compounds to under 1% of original brightness, worse than the first attempt; then dropped to fully transparent (no tint), too little the other way - card boundaries all but vanished and the "different window per scroll position" effect became jarring rather than blending in. 0.25 is the settled middle ground.

Recompute triggers - ResizeObserver is the authoritative one: every .feed-day-card[data-day-index] is observe()d by a single module-level ResizeObserver (a no-op to re-observe an already-observed element) that calls _scheduleDayCoverRecompute() whenever that specific card's rendered size actually changes, for any reason - a CSS-animated panel-collapse transition, a window resize, a font finishing its load and reflowing text, unrelated sibling content shifting the card, anything. This replaced an escalating series of specific-event listeners that each covered one cause found live but not the next: first window.resize/fullscreenchange (debounced via requestAnimationFrame plus a setTimeout(..., 400) follow-up, since a single rAF can land mid-transition on an animated fullscreen toggle) - didn't cover panel-collapse toggles, since those resize the feed panel without the window itself resizing; then an explicit refreshDayCoverFlows() hook wired into prefs.js's _setLandingPanelCollapsed() - didn't cover applyPrefs()'s own direct class toggle on initial load (used to apply a returning user's saved panel state, bypassing _setLandingPanelCollapsed() entirely) - then a second hook call added there too - still didn't cover #landing-wrapper's padding transitioning over 0.25s, so even a correctly-fired recompute could measure a mid-animation size. Each fix is still in place as a free immediate nudge for the common cases, but ResizeObserver - watching the actual rendered outcome instead of guessing at every possible cause - is what actually closes this class of bug.

loadFeed() replaces #feed-content's entire subtree on every call (every 60s poll, every SSE-triggered refresh), which would otherwise leak - ResizeObserver doesn't automatically stop observing an element removed from the DOM, so every previous render's day-cards would stay referenced forever as the session goes on. loadFeed() calls _dayCoverResizeObserver?.disconnect() immediately before replacing innerHTML, so each render starts clean before _applyDayCoverFlows re-observes the current cards. No feedback-loop risk from the observer's own callback either - the tiles it inserts are absolutely positioned inside .feed-day-cover-stack, so they never affect .feed-day-card's own layout size, which is what ResizeObserver watches for.

Two earlier, wrong attempts at this were live and reverted rather than just discarded in a draft. Graph layout & physics

On first load (no saved positions): forceAtlas2Based physics runs until stabilisation, then disables and saves all positions to state.positions.

On subsequent loads: physics disabled from the start. Each node update passes physics: false to pin positioned nodes; new nodes get physics: true.

When new nodes are added, syncGraph re-enables physics with stabilization: { fit: false }, runs network.stabilize(300), then on stabilizationIterationsDone saves positions and restores the saved viewport.

Both this handler and initGraph()'s own equivalent (2026-07-25 fix) used to only clear their own tracked reference when they fired, without calling network.off(...) to actually detach - so old listeners stayed attached forever and could accumulate over a long single-session editing spree, each firing (and redundantly calling saveState()) on every later stabilization. Not data loss (all variants converge on the same final positions, and saveState() queues the extra calls), just wasted saves. Fixed by having both handlers detach themselves before nulling their reference.

Drag positions saved to state.positions on dragEnd (1000ms debounce). Pan/zoom saved to state.viewport (500ms debounce on zoom and drag-end when no nodes dragged). Viewport restored once per book open via network.moveTo (guarded by _viewportRestored flag).

Node deletion (graph.js)

subtreeToDelete(rootId) - BFS from root, then removes any node still reachable (without passing through rootId) from a known graph root - originally just state.startSection, but a book can have more than one real root once the alternate-start button ("⚑ Start at a specific section" in play.js) has been used, so the reachability BFS now seeds from state.startSection and every playthrough's own path[0]. Without this, a node with two parents both living only in an alternate-start component (invisible to a BFS rooted at state.startSection alone, since the two components are disjoint) could be wrongly swept up as an orphan even though it's still reachable via its other parent in that same component. Returns a Set of IDs.

deleteNodes(ids):

  1. Removes entries from state.graph and state.positions
  2. Removes id from all choices arrays
  3. Deletes any section left with an empty choices array (now unmapped) - unless it's part of a playthrough path, or carries a note/priority/battle/color/portals worth not silently discarding (same safeguard as play.js's _cleanupOrphanedTargets)
  4. Trims every playthrough's path at the first deleted node it contains - not just the active run. This retroactively reopens (completed = false, result = null) any run whose path passed through a deleted node, including previously-completed wins/losses entirely unrelated to what's currently active. If the active run is one of the trimmed ones, it stops being active - the caller must resume it explicitly. The confirmation dialog does not warn about this retroactive effect on other runs.
  5. Calls saveState() - does not call render() (caller's responsibility)

The caller (boot.js) clears viewingPt only if its own path intersects the deleted set (checked before calling deleteNodes, since the mutation may flip completed on the same object viewingPt references) - not merely because it happens to be incomplete for unrelated reasons. viewingPt and the active run are independent state (the delete button only requires an active, incomplete run to be visible; viewingPt can simultaneously point at any other run), so a plain "is it incomplete" check could clear an unrelated viewed run's overlay just because a node was deleted elsewhere in the active run's tree.

Auto-nav: render()'s choices panel auto-advances through a forced passthrough - secData.choices.length === 1 && !pt.path.includes(secData.choices[0]) && !_suppressAutoNav - scheduling navigate(dest) on a setTimeout(..., 0) (deduped per section via _pendingAutoNavFrom so overlapping render() calls don't each queue a duplicate hop). This is what makes a long chain of single-choice sections "auto-walk" through in one visual beat instead of requiring a click per node.

undoRun() walking past auto-nav sections: pops the current node, then keeps popping past forced (single-choice) nodes until landing on a real decision point (choices.length !== 1) or the run's start. A single-choice node isn't necessarily a forced passthrough though - it could be a real decision the user just recorded (has a note, priority, battle, color, portals, or shown note), so it's worth stopping at one that carries metadata rather than silently skipping past it. But that's only meaningful if auto-nav (above) won't immediately fire for it: once popped, that node's one recorded destination is no longer in pt.path, so if the node itself is a forced single-choice with no metadata, landing there right before its own auto-nav fires just replays the undo's own forward step and sends the user right back where they started (a real bug found live: on a long auto-walked chain, "undo" appeared to do nothing at all). Fixed by computing the same wouldAutoNav check - !pt.path.includes(node.choices[0]) - during the walk-back and only stopping at a metadata node when it's false. This does mean undoRun()'s stopping logic is coupled to render()'s auto-nav condition - if that condition's shape ever changes, this needs to change with it.

Alternate start ("⚑" button): next to New Run, hidden for open-world/series books (_owIsOpenWorld) since those must go through _onNewSeriesRun instead. Public run viewer and alternate starts: getPublicRun/getPublicSeriesRun in server/db.js send a startSection field that public-profile.js's _buildPubSegNetwork uses purely for the cosmetic yellow "start" node marker (isStart, has no effect on layout/traversal - the full path/graph render regardless). Fixed to use that specific run's own pt.path[0] instead, so the public view always highlights wherever that run actually began, not the book's default.

Security note: both endpoints are fully unauthenticated, and both build a multi-book journey by querying every book in the run's series. Own graph view and alternate starts: the same "book default vs. this run's actual start" mismatch existed in three more places, all fixed alongside the public-viewer one above: graph.js's nodeColor()/nodeLabel()/syncGraph() (the private graph's yellow "start" highlight, "START" label, and bold start-node font all now follow _effectiveStartSec(displayPt) - the currently-displayed run's own path[0] when there is one, falling back to state.startSection only when no run is being viewed); graph.js's subtreeToDelete() and play.js's _cleanupOrphanedTargets() (see "Node deletion" - both used to treat state.startSection as the only protected root when deciding whether a node is a safe-to-remove orphan, which could wrongly sweep up a node that's actually still in use from an alternate-start run's own component).

Battle-node coloring drift (2026-07-25): _buildPubSegNetwork's node coloring is one of three independent reimplementations of the same rules (graph.js's nodeColor(), server/export.js's _nodeColor()), and had drifted for the battle flag specifically. Character sheet (charsheet.js)

Self-contained module. Imports only state.js and i18n.js. To remove: delete charsheet.js, remove its import lines from boot.js and play.js, and delete public/css/charsheet.css (and its <link> in index.html).

The sheet is per run. Each playthrough carries charSheet: { fields: [] }. One template per book (state.charSheetTemplate). New runs deep-copy from the template if one exists.

Field types: number, boolean, text, list (comma-separated, stored as string[]), enum (fixed option set per field).

Modal actions: Save writes draft to the active run's sheet; Save as template writes draft to state.charSheetTemplate; Cancel discards draft. Modal is read-only when viewing a completed run - the footer stays visible with Add field/Save/Save as template disabled (not hidden), while Cancel stays enabled so the view can still be dismissed.

Number field formatting: displayed values (compact overlay, read-only modal, editable field when not focused) are comma-formatted via fmtNum() (toLocaleString()). The editable input is type="text" inputmode="numeric" rather than a native number input, since native number inputs can't display thousands separators - focus/blur handlers swap between the raw digit string and the comma-formatted string. Because a text input accepts any keystroke, readVal's number case live-filters to [0-9.\-] and falls back to 0 on an unparseable result, so garbage input can't get stored or displayed as a literal "NaN". The ± stepper buttons strip commas before parsing and reformat afterward.

This convention was violated in battlesim8.js (2026-07-25) - its stat inputs and arrows counter used bare type="number" despite sitting in the same .inv-qty-wrap/±-button markup as the correctly-built steppers elsewhere. Fixed to type="text" inputmode="numeric" with a live [^0-9] filter (no comma-formatting needed - these are always small values). Same violation found and fixed the same way in battlesim829.js (stat inputs, bsim-ranged-attempts, bsim-heal-amount - the latter had no input listener at all before this).

Identifier validation (edit-book.js)

validateIsbn(raw)

Strips hyphens and spaces, uppercases. Empty string → '' (optional). 10 chars → ISBN-10 mod-11 check (allows X as 10th digit). 13 chars → ISBN-13 alternating-weight check. Anything else → null (invalid). Returns digits-only normalised string.

validateIssn(raw)

Strips hyphens and spaces, uppercases. Empty → ''. 8 chars (digits + optional trailing X) → mod-11 check with weights 8–2. Returns formatted XXXX-XXXX. Otherwise → null.

validateAsin(raw)

Strips spaces, uppercases. Empty → ''. Exactly 10 alphanumeric characters ([A-Z0-9]) → valid. No checksum exists for ASINs. Otherwise → null.

null triggers an inline error; '' is stored as NULL.

HTML generator (buildBookHtml(book, username, itemsById))

Self-contained, print-friendly HTML. Inline CSS only. itemsById is a Map<id, {name, type}> for resolving item names (defaults to empty map, shows "Item #N" fallback). Contains:

  • Summary stats: mapped, discovered-only, runs, wins, losses, battle deaths, in-progress
  • Playthroughs table: run number, result, date, full section path (→-separated; ✝ death, ★ victory)
