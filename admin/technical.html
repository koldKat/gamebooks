CSS file split (2026-07-18)

style.css had grown to 9,238 lines - one file for the whole app. Split into 15 per-module files (one per like-named JS module) plus style.css itself, now 549 lines of shared/base rules only. public-profile.css is shared by both public-profile.js and covers.js (cover activity view lives in the same #public-modal markup both use).

Unlike JS, there's no import-cascade to maintain between stylesheets - each is an independent <link>, so a changed CSS file only needs its own ?v=N bumped. reduce-motion.css and mobile.css are cross-cutting overrides rather than one module's styling, so they're deliberately the last two <link> tags in index.html - an improvement over the original file, where those two sections sat at arbitrary mid-file positions.

Verified via exact line-range extraction plus a line-count reconciliation (sum of all new files + planned remainder must equal the original total) before every trim of the source file - this caught two real extraction mistakes before they reached the live file. See project_refactor_main.md memory for the full account.

Full-viewport mobile modals need 100dvh, not 100vh: 100vh is sized against the browser's largest possible viewport (address bar hidden); when the address bar reappears the actual visible area shrinks below that stale figure, and a fixed-height/fixed-position modal overflows past the top of the screen, hiding its header/close button behind the address bar. Fix is to declare the property twice - 100vh first as a fallback, 100dvh immediately after (ignored by browsers that don't support it). Applies to #forum-modal (charsheet.css) and .pub-modal/.pub-modal--run/.modal-inner/#stats-modal (mobile.css).

server.js's computeCodeStats() (feeds "Lines of code"/"Code size" in Stats for Nerds) scans the public/css//public/js/admin directories dynamically, not a hardcoded file list - it's a one-time IIFE at module load, so a new file needs a server restart to be picked up.

Server file structure

server.js and server/db.js hold requires/bootstrap/Router/DDL only; per-domain logic is split module-by-module (see the frontend module dependency graph). Same process for any future extraction: build each new module fully, verify it, wire it in, delete the old code from the monolith last - never a bulk line-range removal.

server/db.js is a thin barrel: every raw CREATE TABLE/ALTER TABLE/one-time-migration block stays physically in db.js, in its original relative order (some migrations reference tables/functions defined later in the file - reordering the DDL is unsafe against production's live database). Only the function definitions live in server/db/*.js domain modules (see project structure above), each require()-d back into db.js. db.js's module.exports re-exports all of them.

server.js holds requires, one-time bootstrap, the Router (regex route-pattern constants + dispatch function), and httpServer.listen(...). Everything else is in server/*.js (cross-cutting: SSE, email, request helpers, runtime/process state, static file serving) and server/routes/*.js (per-domain HTTP handlers). Mutable process state (maintenance-mode flag, traffic counters, CPU/memory averages, uptime timestamps) lives in server/runtime-state.js behind getter/setter accessors, since raw let variables can't be shared across CommonJS modules by reference.

Admin panel JS structure

admin/index.html loads admin/js/boot.js as a module entrypoint; per-domain logic is split into 10 modules under admin/js/ (see project structure above).

Serving mechanism: server/routes/admin.js's serveAdminFile() infers Content-Type from the filename extension (.js → text/javascript, else text/html) - required, since browsers reject <script type="module"> if the response's MIME type isn't a JS type. server.js has GET /admin/js/:file (regex-restricted to [a-zA-Z0-9_-]+\.js, no path-traversal risk), gated by the same requireLocalhost as the rest of the admin panel; these files stay reachable during maintenance mode too, same as the rest of the admin panel.

users-books.js (Users tab, Books tab, both detail views, Gift modal) is deliberately not split further: the user-detail and book-detail views call back into each other constantly, so they stay one module rather than being forced into users.js/books.js. It imports loadAll/loadTools from dashboard.js, which itself imports loadUsers/loadBooks back from users-books.js - a circular import, safe in ES modules as long as the imported bindings are only read inside function bodies that run later, never at module-evaluation time.

feedback.js is the one module with a real gotcha: its feed-card HTML uses inline onclick="toggleFeedbackCard(this)" (built via innerHTML templates), which resolves against window, not module scope - fixed with an explicit window.toggleFeedbackCard = ... at the bottom of the file (and two more for its sibling handlers). Everything else uses addEventListener.

Server

server.js is a plain Node.js HTTP server. It serves static files from public/ and exposes a JSON REST API. Routes are matched manually with regex - no express or other framework.

Listens on port 443 (HTTPS) when a Let's Encrypt certificate exists at /etc/letsencrypt/live/koldkat.net/, otherwise falls back to port 3000 (HTTP). Port overridable via PORT env var. HTTP port (redirect) defaults to 80, overridable via HTTP_PORT.

coinsBalance = floor(xp/1000) + bonus_coins - coins_spent. xpBoostPct is the actual boost percent (DB stores tenths; divided by 10 before returning). xpBoostPurchased is the count of purchased boosts only (free level-up boosts excluded). bonusHeartbeatXp counts purchased Heartbeat XP upgrades (+0.1 base heartbeat XP each). isAdmin is returned so the regular app can reliably show admin-only controls such as PDF rows. pdfAccess is true when users.pdf_access = 1 (or when isAdmin is true); when true the frontend renders a small PDF link next to the book title in the play area (if the book has a PDF), opening it in a new tab.

The client-side XP / coin reward floater uses repeated GET /api/profile snapshots. rewards.js compares the latest { xp, coinsBalance } values against the previous snapshot and renders a merged floating notice in #reward-float-layer when either value increases. There is no dedicated server push channel for this.

The floater layer's horizontal position is computed at runtime from measured element positions rather than pure CSS, since the correct centering gap depends on which screen is showing (books/landing vs. the play area).

Book PDFs

PDF files are stored in public/books/<bookId>_<timestamp>.pdf and served via GET /books/<filename>.

  • POST /api/books/:id/pdf - raw PDF body, max 128 MB. Magic bytes %PDF validated. Old file deleted on replacement. Awards 200 XP (pdf_available) to every user who has the book in their library (once per user per book).
  • DELETE /api/books/:id/pdf - removes the file and clears pdf_path. Does not revoke previously awarded XP.

The pdf_path column on books stores the filename only.

The static file gate (GET /books/:path) requires the request to be authenticated with a user who has is_admin = 1 or pdf_access = 1. Gold Coins: base GC is still derived from XP, but extra one-time milestone GC rewards are stored separately in users.bonus_coins and deduped in coin_events.

  • playtime_24h - 1 GC each time a user crosses another 1,440 idle_heartbeat events (24 tracked hours)
  • book_completed - 1 GC the first time a user earns visit_all for a book
  • runs_milestone - 1 GC per 100 completed runs (win_run + death_run + battle_run events total); ref is the milestone as a string ("100", "200", …). Checked at runtime after every run-completing state save and backfilled once at startup.
  • visit_all_series - N GC (N = child book count) the first time a user earns visit_all for every non-container book in a series
  • visit_all_anthology - N GC (N = child book count) the first time a user earns visit_all for every child book of an anthology

Startup backfills for book_completed, runs_milestone, visit_all_series, and visit_all_anthology run once, guarded by book_complete_coin_backfilled, runs_milestone_coin_backfilled, and group_complete_coin_backfilled keys in admin_settings.

Bonus GC lottery (_rollBonusGc/claimBonusGc in xp.js, added 2026-08-08): every genuine XP event (gated on the same xp_events dedup insert's r.changes > 0 that guards level-up processing, so repeated calls for an already-recorded event/ref never roll twice) rolls a chance of a bonus gold coin appearing: (level + min(bonus_gc_chance_purchased, level)) × 0.0001 - 0.01% per level, plus up to another 0.01% per level from shop purchases (gc_chance item above), uncapped on the level side. Rolls happen for every event type including idle_heartbeat; the roll is skipped entirely (not discarded) while a coin is already pending - only one can wait at a time. A successful roll just sets users.pending_bonus_gc = 1. _rollBonusGc takes pending/gcChancePurchased as arguments rather than running its own SELECT - _awardXpTx already fetches both in its own before row at the top of the transaction, and this fires on every single XP event, so it deliberately reuses that instead of adding a second query to an already-hot path. claimBonusGc(userId) (one transaction: clear the flag, then awardCoins(userId, 'bonus_gc_claim', Date.now(), 1)) is the only way it becomes an actual coin. No position/on-screen state is tracked server-side - pending_bonus_gc is a pure boolean; the client (#bonus-gc-btn, fixed spot in the app banner, greyed out until getUserXpInfo().pendingBonusGc is true) is the only place "where" it visually appears. The ready state pulses (bonus-gc-pulse, 4s ease-in-out infinite - same rate as #notif-btn/#forum-btn's own notif-pulse, gated behind body.reduce-motion in reduce-motion.css the same way those are) rather than just glowing statically, matching the app's existing "something's waiting for you" convention. While nothing's pending, the button's tooltip shows the player's current total chance (shop.js's _bonusGcChancePct(), a display-only mirror of the server formula above) via a separate i18n key (bonus_gc.tooltip_empty_pct, distinct from the plain bonus_gc.tooltip_empty used as the static HTML fallback) - applyTranslations()'s generic data-i18n-tooltip pass calls t() with no params, so a {pct} placeholder in that same key would render as the literal string {pct}% until the first real data fetch overwrote it; keeping them separate avoids that. The tooltip also shows the player's lifetime claimed count ({claimed} in the same key), sourced from getUserXpInfo()'s bonusGcClaimed (a SUM(amount) over coin_events filtered to event = 'bonus_gc_claim').

Lucky-coin generated/claimed tracking: users.bonus_gc_generated (added alongside pending_bonus_gc) is a lifetime counter incremented every time _rollBonusGc actually rolls a coin into existence, separate from coin_events' bonus_gc_claim rows which only track successful claims - the gap between the two (generated minus claimed) is coins currently sitting unclaimed across all players. Because this column didn't exist when the feature first shipped, server/db.js backfills it once (idempotently, via MAX() so it only ever raises the floor) to claimed + pending_bonus_gc for every user on boot - a claim always implies a prior generation, and a currently-pending flag implies one more generation that hasn't been claimed yet, so that's a safe historical floor even though the exact pre-column generation count is lost. Both adminGetStats()'s luckyGcGenerated/luckyGcClaimed (admin dashboard's "Lucky coins generated / claimed" card) and adminGetUsers()'s per-user luckyClaimed (Users table's "Lucky" column) read from these same two sources - the per-user value reuses getUserXpInfo()'s already-computed bonusGcClaimed rather than running a second identical query.

XP & levelling

XP is stored in users.xp. Every awarded event is recorded in xp_events with a UNIQUE constraint on (user_id, event, ref) - XP can never be double-awarded.

Level formula

xpForLevel(n)    = 1000 × n × (n+1) / 2
computeLevel(xp) = min(floor((-1 + sqrt(1 + 8·xp/1000)) / 2), 100)

Level 1 = 1,000 XP · Level 10 = 55,000 · Level 100 = 5,050,000 (cap)

Undo & fast travel limits

Both maxUndos() and maxFastTravels() follow the same formula: 3 at levels 0–30, then +1 per 10 levels from level 31 (thresholds: 31, 41, 51, 61, 71, 81, 91), capped at 10. When a level-up crosses a threshold, the feed announces it as a · +1 undo & fast travel unlocked (N per run) suffix on the level-up entry.

Reward dedup refs: death_run/battle_run/win_run/share_run/charsheet_run/charsheet_saved key their xp_events dedup ref off the run's startedAt timestamp (array index only as a fallback for runs predating this field) - startedAt is assigned once at creation and never reused, so it can't collide the way an array index can once a run at that slot is deleted and a new one takes its place. The ref's prefix depends on whether the book was in an open-world series when that run completed: bookId:startedAt normally, series:seriesId:startedAt for an open-world one - a single book's history can contain both. Anything resolving "the run behind this ref" (getFeed()'s first_win/first_loss/first_battle_death lookup, via _getFirstRunRef/_runKeyFromRef) must check both prefixes, not just the book-scoped one.

better-sqlite3 gotcha: never concatenate a bound JS-number parameter into a LIKE pattern in SQL ('series:' || ? || ':%' with a number bound to that ?) - better-sqlite3 binds a plain JS number as SQLite REAL by default, and concatenating a REAL stringifies it with a trailing .0 ('series:123.0:%' instead of 'series:123:%'), so the pattern silently never matches. CAST(? AS TEXT) does not fix this - casting an already-REAL-bound value still produces "123.0". Only String()-ing the value in JS before binding actually works. This exact bug shipped in _getFirstRunRef's seriesId param and caused a real duplicate feed entry ("won series run N" and "won ... for the first time" shown separately for the same win). Build the whole pattern string in JS first instead (`${bookId}:%`), as most of the codebase already does - it sidesteps this entirely.

run_depth is the deliberate exception - stays index-based (${bookId}:${i} / series:${owSeriesId}:${i}), do not "fix" it to match the others. run_depth (~25 XP) fires the instant any run has a non-empty path, i.e. essentially on creation - a guaranteed-unique ref would make it directly farmable (create a run, get the XP, delete it, repeat). Plain index-based dedup is intended: re-creating a run at the same slot after deleting it does not re-earn run_depth, while a genuinely new slot does. Do not run the one-time correction scripts in scripts/ (revoke_duplicate_run_depth.js, restore_run_depth_correction.js, backfill_run_reward_refs.js) again.

Completion percentage floor rule

Every "N out of total (X%)" display in the app shows 100% only when n >= total exactly; otherwise the percentage is floored and capped at 99% (Math.min(99, Math.floor(n / total * 100))), never rounded up - prevents e.g. 318/319 sections displaying as a misleading "100%". Implemented independently (not centralized) in books.js (_bookItemHtml, series/anthology aggregate, stash aggregate), play.js (updateStats › pct), and stats.js (the shared pct helper).

Password hashing & sessions

Password hashing

crypto.scrypt (Node built-in, promisified) with a random 16-byte hex salt. Stored as { password_hash, salt }. Verification uses crypto.timingSafeEqual.

Sessions

Random 32-byte hex token stored in sessions table. Sent to client on login/register; stored in localStorage under gamebook_auth_token.

Sessions expire 7 days after creation (expires_at = created_at + 604800). getSession rejects expired tokens → client receives 401 and is redirected to login. Expired rows are deleted on server startup and on Vacuum.

Impersonation sessions must stay invisible to activity tracking and rewards. Sessions carry an is_impersonation flag (createSession(userId, { impersonation: true }), set from the admin panel's impersonate link). authenticate()/authenticateOptional() (request-helpers.js) skip updateUserLastActive() for these sessions, but that alone isn't enough - adminGetUsers()'s last_active column falls back to MAX(user_books.updated_at) for users with no last_active_at yet, and ordinary state saves while impersonating bump that timestamp too. handleSaveState checks isRequestImpersonating(req) and passes { skipTimestamp: true } to saveBookState() to close that gap.

XP/coins are enforced centrally rather than per-route: server/impersonation-context.js wraps every request in an AsyncLocalStorage context (runWithImpersonationContext, applied once in server.js's top-level request handler), and server/db/xp.js's awardXp/awardCoins both check isImpersonatingContext() and no-op if the current request is impersonated - this covers every award call anywhere in that request's async chain (including processStateXp, party fan-out, and anything added later) without each one needing its own check. A few call sites also short-circuit earlier as a redundant belt-and-suspenders layer (handleSaveState's processStateXp call, the party-state fan-out loop, GET /api/feed's idle-heartbeat award, acceptPartyInvite's skipXp option) - the central check makes these optional, not load-bearing, but they're cheap and avoid pointless work. A prior version of this contract relied entirely on individually guarding each award call site, which is what let real XP leak to impersonated accounts (and, via party fan-out, to real party members) for a while despite the "fix" already being merged - a route or db function added afterward simply wasn't covered.

Rate limiting

IP-level: Max 10 failed auth attempts per IP per 15 minutes. Tracked in memory (_authFailures Map); stale entries evicted on a 15-minute interval. Returns 429.

Account-level: After 5 consecutive failed login attempts, the account is temporarily locked for 15 minutes (locked_until = now + 900). Returns 403 with a descriptive message. failed_login_attempts resets to 0 on successful login or when the temp lock expires. Admin can hard-lock any non-protected account (locked_until = -1); hard locks never auto-clear. Protected accounts skip all lock logic.

Image upload security

Avatars and book covers are validated for magic bytes (JPEG, PNG, GIF, WebP) and compressed client-side to ≤256 KB before upload. Server enforces a 300 KB raw body limit.

Portal-created playthroughs: every place that creates a target-book playthrough placeholder for a portal (_syncSeriesRuns's pad-to-needed loop, and startPortalRun's own fallback in play.js) must call instantiateLoadout() for inventory/equipment/equipmentVisible - a placeholder missing these silently loses the player's starting gear the moment they portal into a book for the first time. Playthroughs whose path[0] gets set by portal entry (rather than a genuine choice made by the player) are marked portalEntry: true, so graph.js's _effectiveStartSec knows to keep showing the book's real state.startSection as the "START" node instead of mistaking the portal's entry section for a deliberate alt-start.

Reusing an existing placeholder slot must stamp startedAt before touching path: _handleNewSeriesRun's while (state.playthroughs.length <= run_index) loop only extends the array if it's too short - if a slot at run_index already exists as an untouched _syncSeriesRuns padding placeholder (startedAt: null), the loop does nothing and the function used to push the start section straight into that placeholder's path without ever stamping startedAt, reproducing the same "phantom looks touched" bug described under Data migration above. Fixed by stamping startedAt unconditionally right where pt is resolved, before touching path - matching the pattern startPortalRun/doJumpCrossBook already use.

Completion must only sync onto the book that actually ran it: _syncSeriesRuns propagates a completed series_runs row's completed/result onto local state_data playthroughs, but only for a book whose own placeholder at that run index was actually touched (pt.path.length > 0 || pt.startedAt). Every book in the series carries a placeholder for every run index so numbers stay aligned, but only the book(s) the run actually visited may have their placeholder marked complete - copying it onto an untouched placeholder made that book's own next save look like a genuine new completion to handleSaveState, which re-awarded XP and re-stamped series_runs.completed_at to that later save's time (which also scrambled feed ordering, since entries sort by that timestamp). handleSaveState mirrors the same guard server-side (newPt.path?.length > 0) before treating a playthrough as newly-terminal, so stale already-leaked data can't retrigger it either.

processStateXp (server/db/xp.js) has the same guard, independently. Its own per-run loop (death_run/win_run/battle_run, first_loss/first_win, share_run, charsheet_saved/charsheet_run, add_charsheet_field) and its reconciliation safety net both skip any playthrough that isn't "touched" (pt.path?.length > 0 || pt.startedAt) before awarding anything for it - a leaked/stale placeholder still gets its charSheet mirrored onto it for display (_syncSeriesRuns sets pt.charSheet = sr.char_data unconditionally, outside the touched check, since the character is meant to travel with the series), so without this guard add_charsheet_field in particular could re-award XP for fields that only exist there because they were mirrored in, not genuinely added in this book. Uses startedAt (not path.length alone) so a brand-new real run that hasn't made its first choice yet still earns day-one charsheet-edit XP.

Pre-series runs: the first time a book's series turns open-world, migratePreSeriesRuns (server) and _syncSeriesRuns (client, mirrors the same logic as a fallback) move any pre-existing runs out of playthroughs into state_data.preSeriesRuns, since open-world's own run slots need playthroughs[i] to line up index-for-index with series_runs. activePtIndex is reindexed (or nulled if the active run itself was migrated) rather than left dangling. preSeriesRuns still counts in getProfileStats()/adminGetUsers(), still generates run_completed (and first_win/first_loss/first_battle_death via _resolveRunIndex) entries in getFeed() - deliberately not gated on seriesIsOpenWorld like the playthroughs loop is, since these runs never get a series_run_completed entry either - and is still reachable for public viewing (getPublicProfile, getPublicRun, getBookActivity) via a negative runIndex - matching the client's own "Run -N" display convention. The URL route (publicRunRe in server.js) allows a leading - for this reason.

getProfileStats() and getPublicProfile() (both server/db/feed.js) also agree on totalBooks/createdBooks: anthology children are excluded, so an anthology counts as one book regardless of how many of its children the user has added.

getSiteStats()'s levelUps (Stats for Nerds' "Total levels") and getAppXpSummary()'s sumLevels (the App-wide XP widget) are both a live SUM of every user's current level, computed identically - deliberately not a COUNT of level_up xp_events, since that log is deduped per (user, level) to block farming the level-up coin bonus and can undercount after any XP correction.

Modal close-on-outside-click convention

Every modal closes on backdrop click via a click listener checking e.target === overlay. Since a click fires based on mouse-release position, not press, dragging from inside a modal (e.g. panning a graph) and releasing outside would otherwise register as a click on the overlay and close it mid-drag. Fix: track mousedown separately, only treat a backdrop click as real if the preceding mousedown also landed on the overlay.

#public-modal-overlay/#guide-modal-overlay (boot.js) share one module-level _mousedownOnOverlay tracker, set by a single document-level mousedown listener checking e.target.classList.contains('modal-overlay' | 'pub-overlay' | 'inv-overlay') - any overlay needs one of those three classes to participate. #feedback-modal-overlay, #stats-modal-overlay, the notebook overlay, and the equipment/inventory item-picker overlays each keep their own local tracker instead, since a mousedown/click pair only applies to the one element it's attached to.

Forum modal reveal-after-load (boot.js): #forum-modal-frame is a persistent <iframe src="/forum"> - a link clicked inside it navigates contentWindow's own location without ever touching the <iframe> element's src attribute, so openForumModal() always force-resets it back to /forum via contentWindow.location.replace() on every open (comparing against getAttribute('src') would miss any in-iframe navigation entirely). That reset is only revealed (forumOverlay.classList.add('active')) once the iframe's load event actually fires, not immediately - revealing right away left whatever thread/category was still rendered from the previous session visible for a brief moment before the reset page replaced it. The pending load listener is tracked in a module-level _forumRevealPending + _cancelForumReveal() (top of file, above navigateToBook), and every path that can close or navigate away from the forum modal - closeForumModal() (close button/Escape/backdrop), navigateToBook(), and showBooks() - calls _cancelForumReveal(), not just the one wired to the close button. Without that, closing the modal before the reset finished loading didn't actually stop anything: the listener still fired moments later and reopened the modal on its own.

Graph layout & physics

On first load (no saved positions): forceAtlas2Based physics runs until stabilisation, then disables and saves all positions to state.positions.

On subsequent loads: physics disabled from the start. Each node update passes physics: false to pin positioned nodes; new nodes get physics: true.

When new nodes are added, syncGraph re-enables physics with stabilization: { fit: false }, runs network.stabilize(300), then on stabilizationIterationsDone saves positions and restores the saved viewport.

Gotcha: every stabilizationIterationsDone handler must call network.off('stabilizationIterationsDone', ...) on itself right before nulling its own tracked reference, not just null the reference - the "unregister before starting a new one" guard only tracks the most recently registered handler, so an already-fired-and-self-nulled one that skipped network.off() stays attached forever and can fire again alongside future handlers.

Drag positions saved to state.positions on dragEnd (1000ms debounce). Pan/zoom saved to state.viewport (500ms debounce on zoom and drag-end when no nodes dragged). Viewport restored once per book open via network.moveTo (guarded by _viewportRestored flag).

Node deletion (graph.js)

subtreeToDelete(rootId) - BFS from root, then removes any node still reachable (without passing through rootId) from a known graph root. The reachability BFS seeds from state.startSection and every playthrough's own path[0], since a book can have more than one real root once the alternate-start button ("⚑ Start at a specific section" in play.js) has been used, and each alternate-start component is otherwise disjoint from a BFS rooted at state.startSection alone. Returns a Set of IDs.

deleteNodes(ids):

  1. Removes entries from state.graph and state.positions
  2. Removes id from all choices arrays
  3. Deletes any section left with an empty choices array (now unmapped) - unless it's part of a playthrough path, or carries a note/priority/battle/color/portals/showNote worth not silently discarding. Three other places apply the identical "worth keeping" check on their own single node: play.js's _cleanupOrphanedTargets, boot.js's _pruneDiscovered (runs after toggling priority/battle/color), and the note modal's own save handler in play.js (runs after clearing a note). All four must check the same metadata list, or one of them will silently wipe a node - real bug, twice: both _pruneDiscovered and the note-modal handler were missing portals, deleting a node's portal the moment its note or priority/battle/color was cleared if it had no other choices.
  4. Trims every playthrough's path at the first deleted node it contains - not just the active run. This retroactively reopens (completed = false, result = null) any run whose path passed through a deleted node, including previously-completed wins/losses entirely unrelated to what's currently active. If the active run is one of the trimmed ones, it stops being active - the caller must resume it explicitly. The confirmation dialog does not warn about this retroactive effect on other runs.
  5. Calls saveState() - does not call render() (caller's responsibility)

The caller (boot.js) clears viewingPt only if its own path intersects the deleted set (checked before calling deleteNodes, since the mutation may flip completed on the same object viewingPt references) - not merely because it happens to be incomplete for unrelated reasons. viewingPt and the active run are independent state (the delete button only requires an active, incomplete run to be visible; viewingPt can simultaneously point at any other run), so a plain "is it incomplete" check could clear an unrelated viewed run's overlay just because a node was deleted elsewhere in the active run's tree.

Two deliberate exceptions, both because navigate(dest) calls endPlaythrough() immediately for a terminal dest: the destination itself being a terminal (-1/0) is never auto-navigated into, since a straight single-choice line from the start section into a death/win would otherwise resolve the whole run with zero player interaction before they could even register what happened; and a section with a portal also suppresses auto-nav, since otherwise a forced death/win that's also a portal would always resolve as the death/win before the player ever saw the portal option. navigate()'s own willAutoNav (used only to skip a redundant graph-focus animation) and undoRun()'s wouldAutoNav must both mirror this exact condition or they'll disagree with what actually happens.

A single-choice node isn't necessarily a forced passthrough though - it could be a real decision the user just recorded, so it's worth stopping at one that carries metadata (note, priority, battle, color, portals, shown note) rather than silently skipping past it - but only when that stop wouldn't immediately re-trigger auto-nav (the same wouldAutoNav check, !pt.path.includes(node.choices[0]), computed during the walk-back). undoRun()'s stopping logic is coupled to render()'s auto-nav condition - if that condition's shape changes, this needs to change with it.

Grid overlay + snap: drawGrid in graph.js is registered on vis-network's beforeDrawing event (under nodes/edges, unlike the note/priority/battle overlays which use afterDrawing). Spacing is a fixed constant, GRID_SIZE, not user-configurable. Snap on new nodes: _assignLocalPositions() (auto-placement for newly-added nodes on a book that already has a saved layout, in graph.js) also snaps its output when state.snapToGrid is on, after _chooseLocalPosition()'s overlap-avoidance scoring runs against the real, unrounded neighbor positions - not before, so rounding doesn't skew the scoring itself. A freshly-added node was never hand-placed by the user, so this doesn't conflict with "snap never retroactive"; there's no existing deliberate placement to disturb. The one accepted trade-off: rounding can occasionally land a new node a little closer to a neighbor than the scoring intended, same as the drag-end snap already accepts.

Identifier validation (edit-book.js)

validateIsbn(raw)

Strips hyphens and spaces, uppercases. Empty string → '' (optional). 10 chars → ISBN-10 mod-11 check (allows X as 10th digit). 13 chars → ISBN-13 alternating-weight check. Anything else → null (invalid). Returns digits-only normalised string.

validateIssn(raw)

Strips hyphens and spaces, uppercases. Empty → ''. 8 chars (digits + optional trailing X) → mod-11 check with weights 8–2. Returns formatted XXXX-XXXX. Otherwise → null.

validateAsin(raw)

Strips spaces, uppercases. Empty → ''. Exactly 10 alphanumeric characters ([A-Z0-9]) → valid. No checksum exists for ASINs. Otherwise → null.

null triggers an inline error; '' is stored as NULL.

Graph snapshots are SVG, generated entirely server-side (buildGraphSvg in server/export.js) from each book's already-saved state.positions/state.graph/state.playthroughs/state.startSection - no browser, canvas, or headless renderer, and no client round-trip. An earlier version rendered a live vis.Network off-screen in the browser and POSTed a captured PNG back; that was dropped because a <canvas> capture is only ever as sharp as its pixel size (blurry vs. resolution-independent SVG), and positions/colors are just data - a browser was never actually needed to lay anything out. Removing the round-trip also let /api/export/all go back to a single GET request.

Node/edge coloring in buildGraphSvg is a parameterized reimplementation of graph.js's nodeColor()/edgeColor() (the "no specific run being viewed" aggregate-coloring branch, since a static snapshot has no single displayed run) - not imported from graph.js, which is coupled to the single live state singleton on the client and has no server-side equivalent. Graph legend: the exported HTML embeds _exportLegendHtml() directly under the graph image in buildBookHtml() whenever book._hasGraph is set, so the export stands on its own outside the app.

Edges honor the book's own connectorStyle (_curveControlPoint mirrors graph.js's CONNECTOR_STYLES - curvedCW/CCW bow perpendicular via a quadratic Bézier control point; cubic/horizontal are approximated as a CW curve rather than left straight; straight draws a plain line). Node labels render below the node, matching vis-network's actual default for dot-shaped nodes (never inside the dot). The root <svg> sets explicit width and height, scaled so whichever dimension is larger is capped at 1600 - a tall narrow graph gets its height capped instead of stretching width and leaving height to the viewer's guess, which is what caused huge blank margins/scrollbars when opening the file directly.

HTML generator (buildBookHtml(book, username, itemsById))

Self-contained, print-friendly HTML. Inline CSS only. itemsById is a Map<id, {name, type}> for resolving item names (defaults to empty map, shows "Item #N" fallback). Contains:

  • Book metadata table (authors, identifiers, pages, description, discoverable sections if set, series name + open-world flag if in a series)
  • Summary stats: mapped, discovered-only, runs, wins, losses, battle deaths, in-progress
  • Playthroughs table: run number, result, date, full section path (→-separated; ✝ death, ★ victory)
  • Per-run <details> blocks (collapsed by default): charsheet fields, inventory with qty/note, equipment with slot label/item name/qty/label/note
  • Section map: every known section with choices, priority flag, battle flag, and note

Open-world series runs: every book in an open-world series carries one playthroughs slot per series run so numbers stay aligned across books (_syncSeriesRuns, open-world.js), but a run only actually happened in the book(s) it visited - a book's own slot for a run it never touched is a padding placeholder with startedAt: null. buildBookHtml excludes these phantom slots from the summary stats (so they don't inflate a book's run/win/loss counts with runs that happened elsewhere) but still lists them in the Runs table as "played in another book," matching the row numbering the live app uses. A run with result: 'portal' (left this book for another mid-run) counts as still in progress, not finished; a finished run with a leftover portalTarget gets a "(continues in another book)" note, and one with portalEntry: true gets "(started via portal)". state.preSeriesRuns gets its own "Before Joining Series" table/details, using the same negative-index numbering as the live run list, and counts toward the summary stats.

A section counts as mapped if it has real recorded choices, not merely a discovered: true stub (a section can be flagged discovered and still pick up real choices later, so checking the flag alone would undercount). Shared between the "Mapped: N" stat and the section map table split, and mirrors the client's own mappedCount() (state.js) so exported numbers match what the app showed. Works correctly for both numeric and alphanumeric section IDs. Discovered-only sections are listed as "not yet visited" spanning all columns. Full export deduplicates filenames if two books share the same safe name (appends (2), (3), etc.). All strings HTML-escaped.

safeFilename rejects Windows-reserved device names (CON, PRN, AUX, NUL, COM1-9, LPT1-9, case-insensitive, with or without an extension) and caps the result at 150 characters, so an oddly-titled or very long book name can't produce a zip entry that fails to extract or a path near filesystem limits.
